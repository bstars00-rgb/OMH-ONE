# Database Design

PostgreSQL. One schema (`src/lib/db/schema.ts`, Drizzle ORM), two runtimes:

- **Local demo** — PGlite: real PostgreSQL compiled to WebAssembly, persisted to `./.pgdata`. No install, no container, and identical SQL semantics to production.
- **Production** — Supabase Postgres (or any Postgres 14+) via `DATABASE_URL`.

Migrations are plain Postgres SQL in `database/migrations/`, generated by `drizzle-kit`. The same file runs against both.

## Core idea: one base table for every approvable object

```
                      ┌──────────────┐
                      │   requests   │  ← the only table the approval engine knows
                      └──────┬───────┘
                             │ 1:1
   ┌──────────┬──────────────┼──────────────┬───────────────┐
   ▼          ▼              ▼              ▼               ▼
leave_    business_    purchase_      expense_        generic_
requests    trips       requests       claims         requests
```

Every leave, trip, purchase, expense, HR and general approval owns one row in `requests` plus one row in its detail table.

**Why:** the approval engine, inbox, SLA tracking, timeline, comments, attachments, audit log, notifications and analytics are written **once** against `requests`. Adding a seventh request type requires a detail table and a form — no changes to approvals, reporting or permissions. The alternative (a table per type with its own approval columns) would have meant six copies of the approval logic and six versions of every report.

**Cost:** every detail read is a join, and `requests.amount_base` duplicates the detail total. Accepted: the join is on an indexed PK, and the denormalized amount is what makes the inbox and analytics single-table scans instead of six-way unions.

## Tables

### Organization
| Table | Purpose |
|---|---|
| `offices` | Vietnam / Korea / Singapore. Timezone and base currency. |
| `departments` | SCM, GSM, OP, CT, IT, FIN, HR, CEO. `head_employee_id` drives `DEPT_HEAD` routing. |
| `teams` | Sub-unit of a department. |
| `cost_centers` | Charge target, independent of the org tree. |

### People and access
| Table | Purpose |
|---|---|
| `employees` | The person. `manager_id` self-reference drives `MANAGER` routing. |
| `users` | The login. `password_hash` is scrypt with a per-user salt. |
| `user_roles` | Many-to-many. A user can be `FINANCE` and `MANAGER`. |

`employees` and `users` are separate so a person can exist in the org chart (appear in reports, be a `handover_to` target) without being able to sign in.

### Approval
| Table | Purpose |
|---|---|
| `requests` | Base table. Status, priority, amount, current step. |
| `approval_workflows` | Admin-defined route per request type. |
| `approval_workflow_steps` | Template step + condition (`ALWAYS`, `AMOUNT_GT`, `DAYS_GT`, `INTERNATIONAL`). |
| `approval_steps` | **Materialized** step instance bound to a concrete approver, with SLA due date. |
| `approval_actions` | Immutable log of every submit / approve / reject / return / cancel. |

Template steps are copied into `approval_steps` at submission time. Editing a workflow therefore never rewrites the history of requests already in flight — a hard requirement for anything auditable.

### Detail tables
`leave_requests`, `leave_balances`, `holidays` · `business_trips`, `trip_travelers`, `trip_costs` · `purchase_requests`, `purchase_items`, `vendors` · `expense_claims`, `expense_items` · `generic_requests`

### Cross-cutting
`budgets`, `attachments`, `comments`, `notifications`, `ai_reviews`, `ai_conversations`, `ai_messages`, `policies`, `audit_logs`, `exchange_rates`, `system_settings`

## Money

Every monetary row stores **five** columns:

```
currency          original_amount    exchange_rate    base_currency    amount_base
'KRW'             1_385_000.00       1385.000000      'USD'            1000.00
```

The rate is captured at write time and never recalculated. A trip approved last March still reports the dollars it actually cost, not today's conversion. All analytics aggregate `amount_base` (USD) so figures are comparable across offices.

`numeric(14,2)` — never floating point. Drizzle returns `numeric` as a string; `src/lib/money.ts#num()` is the single conversion point.

## Request numbering

`{PREFIX}-{YEAR}-{SEQ}` — `LV-2026-00001`, `BT-2026-00001`, `PR-2026-00001`, `EX-2026-00001`, `HR-2026-00001`, `GA-2026-00001`.

Allocated inside the same transaction as the insert, from `max(seq)` for that prefix and year.

## Duplicate expense detection

`expense_items.receipt_hash = sha256(lower(merchant) | date | amount)`, indexed. On submission the service looks for the same hash on another claim; a hit is surfaced as a `HIGH` risk finding with a link to the original claim. Same-claim duplicates are ignored (splitting one bill across lines is legitimate).

## Budget lifecycle

```
allocated ──► committed ──► spent
             (submitted)   (approved)
```

Approving a purchase or expense moves the amount from `committed` to `spent` in the same transaction as the status change, so the budget can never disagree with the approvals that produced it.

## Indexes

Written for the queries the app actually runs:

- `requests` — `status`, `request_type`, `requester_id`, `department_id`, `submitted_at`
- `approval_steps` — `(approver_id, status)` — the approval-inbox query
- `expense_items` — `receipt_hash` — duplicate detection
- `audit_logs` — `created_at`, `(entity_type, entity_id)`
- `notifications` — `(employee_id, is_read)`

## Security

Authorization is enforced **server-side in SQL**. `requestVisibility(session)` produces a predicate that is `AND`-ed into every request query, so an unauthorized row is never fetched, let alone rendered.

For a Supabase deployment, `database/rls.sql` provides equivalent Row Level Security policies so the same rules hold for any client that reaches Postgres directly (PostgREST, another service). Application-level enforcement and RLS are deliberately redundant: RLS is the backstop if a future query forgets the predicate.

## Extension points

The schema anticipates the modules listed as out of scope:

- `cost_centers` and `budgets` are already the dimensions an Accounting module needs.
- `vendors` is a standalone entity, ready for contracts and AP.
- `attachments.storage_path` is the seam for object storage.
- `requests` accepts a new `request_type` with no engine change — an Asset Request or Contract Approval is a detail table and a form.

## Commands

```bash
npm run db:generate   # schema.ts → database/migrations/*.sql
npm run db:setup      # apply migrations, seed if empty
npm run db:reset      # delete local data, migrate, reseed
```

For Supabase: set `DATABASE_URL`, run `npm run db:setup`, then apply `database/rls.sql` in the SQL editor.
